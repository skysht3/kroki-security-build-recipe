# セキュリティ上の前提・制約

このリポジトリは上流Krokiの非公式ビルド構成です。脆弱性の継続的な修正や安全性を保証しません。

## 検査条件

初回のTrivy検査は次の条件でした。

```text
--severity HIGH,CRITICAL --ignore-unfixed
```

これは「重大度がHIGH/CRITICALで、修正版が存在すると判断されたもの」を表示する条件です。LOW/MEDIUM、修正版未提供、検出漏れ、攻撃到達可能性の評価は含みません。スキャンは最新の脆弱性データベースで都度実行してください。

## Javaと証明書

初回にJava 21.0.13+9を使い、`java -version`とJavaの`cacerts`を確認しました。`emSign Root CA - G1`の存在を確認していますが、eMudhra関連の名前を持つ証明書をすべて削除する運用にはしていません。信頼ストアの更新要否は、その時点のベンダーアドバイザリと対象証明書のフィンガープリントで判断してください。

## イメージレイヤー

本構成は公式Krokiイメージをベースに、Javaディレクトリ、Kroki JAR、D2、Goatを差し替えます。ファイルを削除・上書きしても下位レイヤーの内容は物理的に消えません。古い実行ファイルが実行時に使われないことと、イメージアーカイブから完全に除去されることは異なります。

完全なクリーンビルドとその検証が必要な場合は、上流のDockerfileを新しい依存から組み立てる別方式を検討してください。

## ネットワークと実行

- 公開ポートは`127.0.0.1:8000:8000`などのループバックに限定する例を使います。WSLやOSのファイアウォール構成により実際の到達範囲は異なります。
- `KROKI_SAFE_MODE=secure`を維持してください。既知CVEの代替対策にはなりません。
- TrivyのDockerソケットマウントは`:ro`でもAPI操作権限を強く制限できません。信頼したイメージだけ使用し、CIでは権限を絞った代替も検討してください。
- 新しい版を本番利用する前に、変換形式ごとの試験、ログ、動作上の互換性を確認してください。

## 未対応

Mermaidの補助コンテナはこの構成に含みません。後から追加する場合は、Mermaidイメージ自体の脆弱性検査と、通信構成・変換試験を別途実施してください。
